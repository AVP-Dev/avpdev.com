Когда я проектировал свой органайзер [Nyx Flow](/ru/blog/nyx-building-digital-environment), я сознательно отказался от Telegram Mini Apps в пользу PWA. Причина была не в недостатках Telegram. Мне нужен был рабочий инструмент, доступ к которому не зависел бы от конкретного мессенджера.

Но если изменить исходную задачу — например, дать клиентам возможность записаться на услугу или оформить заказ прямо из привычного чата, — решение может оказаться совершенно другим.

Именно поэтому вопрос «Telegram Mini App или отдельное приложение?» я предпочитаю рассматривать не как спор технологий, а как вопрос архитектуры продукта. Где находится аудитория? Как часто она будет пользоваться сервисом? Какие функции нужны? Что произойдёт, если изменятся правила платформы?

Mini App сокращает путь до первого взаимодействия: пользователю Telegram не обязательно устанавливать отдельное приложение. Однако за это удобство продукт получает дополнительную зависимость — от клиента Telegram, его API и правил.

## 1. Архитектурный стек: что под капотом {#architecture}

Telegram Mini App — это веб-приложение, которое открывается внутри клиента Telegram. Оно размещается на собственной инфраструктуре и может взаимодействовать с мессенджером через JavaScript API (`window.Telegram.WebApp`) или соответствующие SDK.

Важно разделять веб-интерфейс и сам продукт. Telegram предоставляет среду запуска и некоторые возможности взаимодействия с пользователем, но не заменяет сервер, базу данных, бизнес-логику или систему управления заказами.

```text
[ Telegram Client ]
        │  WebApp API: initData, events, theme
        ▼
[ Web Frontend (React / Vite / Next.js) ]
        │  HTTPS: authentication / API requests
        ▼
[ Backend API (Node.js / Go / Python) ] ──▶ [ Database ]
        │
        ├─▶ [ Telegram Bot API ]
        └─▶ [ CRM / Payment Providers ]
```

Если продукт в перспективе должен работать и вне Telegram, я бы не привязывал его бизнес-логику к мессенджеру. Авторизацию через Telegram, уведомления и другие специфичные для платформы возможности можно выделить в отдельные адаптеры.

Тогда веб-интерфейс, Mini App или нативное приложение смогут использовать одно серверное ядро. Это не означает, что с первого дня необходимо поддерживать все три канала. Достаточно не создавать зависимость там, где она не нужна.

### Что важно предусмотреть во фронтенде

1. **Тема оформления.** Учитывать `themeParams` и изменение темы без перезагрузки приложения.
2. **Viewport и safe areas.** Корректно работать с изменением высоты окна, экранной клавиатурой и системными областями экрана. При использовании новых возможностей API учитывать версию клиента.
3. **Производительность.** Ограничивать объём ресурсов первого экрана, загружать тяжёлые компоненты по необходимости и проверять фактическое время запуска на мобильных устройствах.

Выбор React, Vue, Astro или другого инструмента вторичен. Куда важнее то, как приложение ведёт себя в реальной среде, а не только в браузере разработчика.

## 2. Безопасность: где проходит граница доверия {#security}

Telegram передаёт приложению данные об окружении и, в поддерживаемых сценариях запуска, о пользователе. Но сам факт открытия внутри мессенджера ещё не означает, что сервер может доверять всему, что отправляет фронтенд.

Объект `initDataUnsafe` удобен для отображения интерфейса, но не должен служить доказательством личности пользователя. Для серверной авторизации используется исходная строка `initData`, подлинность которой необходимо проверить.

### Алгоритм серверной проверки

1. Извлекаем `hash` и остальные параметры.
2. Формируем строку проверки, сортируя параметры по имени ключа.
3. Вычисляем секретный ключ через HMAC-SHA256 с ключом `WebAppData` и токеном бота в качестве сообщения.
4. Вычисляем HMAC от строки проверки и сравниваем его с полученным хешем.
5. Проверяем `auth_date` с учётом допустимого возраста данных и небольшого расхождения часов.

Пример на TypeScript для Node.js:

```typescript
import crypto from 'node:crypto';

export function verifyTelegramInitData(
  initData: string,
  botToken: string,
): boolean {
  const params = new URLSearchParams(initData);
  const entries = [...params.entries()];

  if (new Set(entries.map(([key]) => key)).size !== entries.length) {
    return false;
  }

  const hash = params.get('hash');
  if (!hash || !/^[a-f0-9]{64}$/i.test(hash)) return false;

  const authDate = Number(params.get('auth_date'));
  const now = Math.floor(Date.now() / 1000);
  const maxAge = 300; // Example policy: five minutes.

  if (!Number.isSafeInteger(authDate) || authDate <= 0 ||
      authDate > now + 30 || now - authDate > maxAge) {
    return false;
  }

  params.delete('hash');
  const checkString = [...params.entries()]
    .sort(([a], [b]) => a < b ? -1 : a > b ? 1 : 0)
    .map(([key, value]) => key + '=' + value)
    .join('\n');

  const secret = crypto.createHmac('sha256', 'WebAppData')
    .update(botToken).digest();
  const expected = crypto.createHmac('sha256', secret)
    .update(checkString).digest();

  return crypto.timingSafeEqual(Buffer.from(hash, 'hex'), expected);
}
```

Пять минут здесь — пример политики для первоначального обмена данными на собственную сессию приложения, а не обязательное ограничение Telegram.

После проверки сервер должен самостоятельно определить пользователя, создать сессию и проверять права доступа к каждой защищённой операции. Подпись подтверждает происхождение и целостность данных, но не заменяет авторизацию.

Проверка времени также не исключает повторное использование перехваченных данных в пределах допустимого интервала. Если сценарий требует одноразового обмена, необходим отдельный механизм контроля повторного использования. Для платежей и других критических операций нужна собственная идемпотентность.

Подробнее: [официальная документация Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## 3. Платежи: Telegram Stars и внешний эквайринг {#payments}

Платёжную модель желательно определить до начала разработки. Она зависит не только от технических возможностей, но и от того, что именно продаёт бизнес.

| Тип товара или услуги | Платёжный инструмент | Что учитывать |
|---|---|---|
| Цифровые товары, подписки и цифровые услуги внутри Telegram | Telegram Stars (XTR) | Правила платформы, стоимость приобретения Stars, условия получения вознаграждения и возвраты |
| Физические товары и офлайн-услуги | Поддерживаемый платёжный провайдер | Доступность в регионе, комиссии, договор с провайдером и требования к расчётам |

Для цифровых товаров и услуг, продаваемых внутри Telegram, платформа требует использовать Stars. Наличие отдельного сайта с эквайрингом не отменяет это требование для продаж внутри мессенджера.

При этом экономику Stars некорректно сводить к единой комиссии в 30%. Стоимость приобретения и итоговое вознаграждение продавца зависят от условий платформы, налогов и способа покупки. Для физических товаров условия определяются выбранным платёжным провайдером.

С инженерной точки зрения важно и другое: открытие окна оплаты не означает, что заказ оплачен. Сервер должен подтверждать оплату по доверенному событию от платформы или платёжного провайдера, сопоставлять его с заказом и корректно обрабатывать повторные уведомления.

Правила и возможности следует сверять с документацией: [цифровые товары и Stars](https://core.telegram.org/bots/payments-stars), [физические товары и услуги](https://core.telegram.org/bots/payments).

## 4. Экономика запуска: из чего складывается стоимость {#pricing}

Mini App позволяет избежать разработки и распространения отдельного нативного клиента, если возможностей веб-интерфейса достаточно. Но интеграции, серверная часть, безопасность и поддержка продукта никуда не исчезают.

На странице [разработки Telegram Mini Apps](/ru/uslugi/telegram-mini-apps) я указываю базовые ориентиры стоимости. Это оценки для конкретного объёма работ, а не универсальные рыночные тарифы.

### 1. Базовый Mini App (от $600, срок от 7 дней)

Витрина услуг, запись, анкеты или сбор заявок. В базовый объём может входить адаптивный веб-интерфейс, серверная проверка данных Telegram, интеграция с ботом и передача заявок в согласованный канал.

Стоимость зависит от количества экранов, логики форм и готовности внешних интеграций.

### 2. Mini App с онлайн-оплатой (от $1 500, ориентир 14–21 день)

Каталог, корзина, оформление заказов, подключение подходящего платёжного инструмента и обработка статусов оплаты.

Бюджет растёт не столько из-за дополнительных экранов, сколько из-за появления новых бизнес-операций: учёта заказов, подтверждения платежей, обработки ошибок, возвратов и синхронизации данных.

### 3. Кастомные экосистемы и Web3 (индивидуальный расчёт, ориентир от 1 месяца)

Корпоративные кабинеты, сложные интеграции, ролевой доступ, синхронизация с учётными системами и специализированные сценарии, включая подключение кошельков, если это допускают правила платформы.

Здесь стоимость определяется требованиями к системе, а не самим фактом её запуска внутри Telegram.

Все сроки предварительные и уточняются после определения границ проекта. Отдельно следует учитывать инфраструктуру, платёжные расходы и [сопровождение после запуска](/ru/blog/site-post-launch).

## 5. Ограничения платформы: что учитывать при выборе {#pitfalls}

Mini App наследует преимущества и ограничения среды, в которой работает.

1. **Доступность и распространение.** Если аудитория уже находится в Telegram, запуск через чат может быть удобен. Но для человека, который не пользуется мессенджером, это дополнительный барьер.
2. **Контроль среды исполнения.** Поведение WebView, разрешения и поддержка API могут различаться между платформами и версиями клиента. Нужно проверять реальные устройства, а не полагаться только на desktop-браузер.
3. **Состояние приложения.** Сеть может пропасть, окно — закрыться. Подтверждение закрытия помогает избежать случайного выхода, но не заменяет сохранение черновиков, корзины и других важных данных.
4. **Зависимость от платформы.** Правила оплаты, доступность функций и способы взаимодействия с пользователем определяет не только разработчик. Собственный сервер и база позволяют контролировать бизнес-данные, но не устраняют зависимость канала доступа от Telegram.

Из этих ограничений складывается вполне практичная матрица выбора:

| Формат | Когда я бы его рассматривал |
|---|---|
| Telegram Mini App | Аудитория уже в Telegram, а ключевой сценарий связан с ботом, сообществом или быстрым взаимодействием из чата |
| PWA / обычное веб-приложение | Нужен самостоятельный веб-продукт, доступный по ссылке независимо от мессенджера |
| Нативное приложение | Продукт требует возможностей ОС, фоновых процессов, глубокой интеграции с устройством или других функций, которые веб не покрывает в нужном объёме |

PWA тоже зависит от браузерных возможностей, а нативное приложение — от ОС и правил распространения. Полной независимости не существует. Вопрос в том, какие зависимости допустимы для конкретного продукта.

## Итог

Я не рассматриваю Telegram Mini Apps как замену вебу или нативной разработке. Это ещё один канал доставки продукта до пользователя, со своими сильными сторонами и ограничениями.

Для Nyx Flow мне важнее самостоятельность инструмента. Для клиентского сервиса, аудитория которого уже находится в Telegram, приоритеты могут быть другими.

Прежде чем выбирать технологию, я бы сформулировал главный пользовательский сценарий и определил, какие части системы должны оставаться независимыми. В идеале изменение канала взаимодействия не должно требовать переписывания всего продукта.

> Хорошая архитектура не устраняет все зависимости. Она позволяет понимать, какие зависимости мы принимаем и почему.
